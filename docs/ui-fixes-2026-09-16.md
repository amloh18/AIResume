## 1. Comms tab — dead space below the email list

**File:** `src/components/dashboard/JobsDashboard.tsx`

> **Correction.** The first pass at this reported the extra `pb-6 sm:pb-10 lg:pb-12` on the wrapper as
> the cause and removed it. That padding was real but **secondary** — the user reported the gap still
> present afterwards. The dominant cause was a stale magic number in the height calculation, below.
> The `pb-*` removal was still correct and is kept.

**Root cause.** The tab content was given a hand-computed height:

```tsx
// before
<div className="h-[calc(100vh-320px)] min-h-[520px] flex flex-col">
```

The `320px` was an estimate of the chrome stacked above the panel. The real total is ~192px:

| component | height |
|---|---|
| global header (`h-14`) | 56px |
| frame top padding (`py-5`) | 20px |
| header block + `pb-4` | ~72px |
| `space-y-6` gap | 24px |
| frame bottom padding (`py-5`) | 20px |
| **total** | **~192px** |

So the wrapper was sized ~128px shorter than the space actually available. Because it was a *fixed*
height rather than a fill, the error scaled with the viewport — measured dead space:

| viewport height | 600px | 700px | 800px | 1000px | 1200px |
|---|---|---|---|---|---|
| dead space (before) | −78px | 22px | 122px | 162px | 162px |

The negative value at 600px is the opposite failure: `min-h-[520px]` forced the wrapper *taller* than
the space available, so the whole page scrolled instead. A magic number fails in both directions.

**Why a flex chain was needed.** Filling the remaining space requires a definite height chain from the
layout frame down to the panel. `OptimizedDashboardLayout.tsx:93` already provides `h-full flex flex-col`,
but the chain breaks at the `JobsDashboard` root, which has no height class — which is exactly why
someone reached for a `100vh` calculation in the first place.

**Fix.** Restore the chain and let flex do the arithmetic:

| element | change |
|---|---|
| root | `+ flex-1 min-h-0 flex flex-col` |
| container | `space-y-6` → `flex-1 min-h-0 flex flex-col gap-6` |
| header block | `+ shrink-0` |
| wrapper | `h-[calc(100vh-320px)] min-h-[520px]` → `flex-1 min-h-0` |

`min-h-0` is load-bearing: without it a flex item refuses to shrink below its content size and the
chain silently does nothing. `gap-6` matches the `space-y-6` (24px) it replaces, so spacing is unchanged.

**Applied conditionally, on purpose.** The root and container are shared by all six tabs, and
constraining them breaks the tall ones. Measured with the chain applied unconditionally, a 2400px
dashboard tab drops `main.scrollHeight` from **2418px to 751px** — no scrollable overflow, content
unreachable. So the chain is gated on `isCommsTab`; every other tab emits byte-identical classes to
before and keeps natural-height, page-scrolling behaviour.

**Result:** dead space is **0px at every tested viewport height** (600–1200px).

## 2. CV thumbnail content width + per-user view persistence

**File:** `src/components/resume-enhancer/steps/Step1Dashboard.tsx`

Two distinct problems were bundled in this report.

### 2a. Width

**Root cause.** The "Your Documents" block hard-coded the standalone-page wrapper even when rendered
in embedded mode:

```tsx
// before — always applied, embedded or not
<div className="w-full max-w-7xl mx-auto px-4 sm:px-8 pb-12">
```

The hero directly above it (line ~1503) already dropped `max-w-7xl mx-auto px-4 sm:px-8` when
`embedded`. So the KPI strip spanned the full dashboard content area while the document grid stayed
pinned to a centred 1280px column — leaving wide empty gutters either side of the thumbnails.

**Fix.** Mirrored the hero's conditional. The grid view was then set to a flat **4 columns from `lg`
upward**, per the follow-up request:

| layout | columns |
|---|---|
| `compact` | `grid-cols-2 sm:3 md:4 lg:5 xl:6 2xl:8` |
| `grid` | `grid-cols-2 sm:2 lg:4` |

Measured rendered column counts (from `gridTemplateColumns`, not inferred from class names):

| viewport | 640px | 768px | 1024px | 1280px | 1536px | 1920px |
|---|---|---|---|---|---|---|
| before | 2 | 2 | **3** | 4 | **5** | **5** |
| after | 2 | 2 | **4** | 4 | **4** | **4** |

Both the loading skeleton and the real grid use the same classes, so there is no column jump when
documents finish loading.

Trade-off worth knowing: a flat 4 columns means the thumbnail grows with the viewport — 229×324px at
1024px, 451×638px at 1920px (bounded by the container's `max-w-[1850px]`). If that reads as too large
on ultrawide, add a `max-w-*` to the grid rather than reintroducing more breakpoints.

### 2b. Persistence (the real fix)

**Root cause.** The chosen view lived only in `localStorage['editor_view_layout']`. localStorage is
device- and browser-scoped, so picking "List" on a laptop had no effect on the same account anywhere
else. The user asked for it to be remembered *for that user*.

**Fix.** Server becomes the source of truth; localStorage is demoted to an instant-paint cache.

- **Store:** `UserSettings.preferences.dashboard.layout` — already existed in the schema with default
  `'grid'`, so no migration was needed.
- **Endpoint:** `src/app/api/user/ui-preferences/route.ts` (new) — `GET` returns the layout, `PATCH`
  validates against `['grid','list','compact']` (400 on bad input) and does a targeted `$set` with
  `upsert: true`.
  Deliberately **not** reusing `PUT /api/user/settings`, because that route writes an `auditLog` entry
  on every call — and a layout toggle fires on every click, which would flood the audit trail.
- **Cache key kept** as `editor_view_layout` so existing users' locally-remembered choice still applies
  on first paint.

**The race.** A naive cache-then-reconcile has a visible failure mode: the user clicks "List" while the
initial `GET` is still in flight, the response arrives with `'grid'`, and the grid snaps back under
their cursor. Two refs resolve it:

| ref | meaning |
|---|---|
| `layoutSyncedRef` | the initial server read has settled |
| `layoutTouchedRef` | the user has picked a layout since mount |

- The `GET` handler **skips applying the server value** if `layoutTouchedRef` is set — the click is
  more recent than the value we asked for.
- The write-back effect gates on `synced || touched`, never on `synced` alone, so a click that lands
  pre-`GET` is still persisted rather than silently dropped.

**Latent bug found while wiring this up.** `PUT /api/user/settings` assigned `preferences` per
top-level key:

```ts
// before — replaces the whole `dashboard` object
userSettings.preferences[key] = settings.preferences[key];
```

Saving *any* preference therefore wiped `dashboard.layout`. Added a deep-merge branch mirroring the
existing `cv` handling in the same file.

## 3. Blur behind the search section

**File:** `src/components/dashboard/JobsDashboard/FiltersBar.tsx`

**Root cause.** The container uses `.job-search-gradient` (orange zigzag pattern,
`globals.css:50-67`) and the controls layered on it are translucent — the search input is
`bg-gray-50/80` (`src/components/ui/input.tsx:66`). The pattern bled through the controls and made the
text noisy.

**The non-obvious part.** `backdrop-filter` blurs everything painted **behind** the element —
*including the element's own ancestor background*. So adding `backdrop-blur` to the container itself
does nothing useful: the gradient is on the container, and the container is not behind itself.

**Fix.** An absolutely-positioned **child** overlay, which sits in front of the container's own
gradient and therefore frosts it:

```tsx
<div
  aria-hidden="true"
  className="absolute inset-0 z-0 rounded-2xl sm:rounded-3xl backdrop-blur-[3px] pointer-events-none"
/>
```

`pointer-events-none` keeps it from swallowing clicks. The three content rows (search bar, nav
switcher, quick-filter bar) then get `relative z-10` so they render above the frost.

Note the overlay is the **first** child, so the container's `space-y-3.5` does not offset it —
`space-y` applies `margin-top` to `* + *`, and the first child has no predecessor.

## 4. Remove the "Needs Attention" skeleton

**File:** `src/components/dashboard/redesigned/NeedsAttentionWidget.tsx`

**Root cause.** The widget is purely additive — it already returned `null` when
`items.length === 0`. But the `if (loading)` branch rendered a full amber-headed placeholder card
while the fetch was in flight, so the dashboard **flashed a "Needs Attention" panel on every load and
then collapsed it** when the list came back empty. On a healthy account that was pure noise on every
single page view.

**Fix.** Removed the `if (loading)` branch, the `loading` state, and both `setLoading` calls (leaving
`loading` declared but unread would have tripped `no-unused-vars`). The widget now renders nothing
until it has real items.

The `error` branch is a separate concern and was left intact — a failed fetch is still worth surfacing.

## Visual verification (CSS harness)

Type-checking, lint and tests cannot verify fixes #1–#4, because all four are *visual*. There is no
running instance of this app locally (port 3000 is a different Express API, 3001 is the Achare CRM Vite
server) and `/dashboard/jobs` needs a live MongoDB plus a NextAuth session, so the app itself could not
be driven.

Instead the CSS mechanics were reproduced in a standalone harness using the **verbatim** gradient from
`globals.css:50-67` and the real translucent control colours, then rendered in headless Chromium at
2× DPR and measured in pixels.

### Fix 3 — does the frosted overlay actually work?

The claim under test: `backdrop-filter` blurs what is painted behind the element *including the
element's own ancestor background*, so the frost must be a child, not a class on the container.
Measured as mean `|p(x+1,y) − p(x,y)|` (edge energy) over the pattern:

| measurement | bare gradient | with `blur(3px)` frost | change |
|---|---|---|---|
| **isolated gradient probe** (pattern only) | 0.664 | 0.213 | **−68.0%** |
| full search panel, light | 2.289 | 1.975 | −13.7% |
| full search panel, dark | 2.199 | 1.916 | −12.9% |

The isolated probe is the meaningful number. The full-panel figures are **diluted** by the sharp
control edges (input border, text, pill outlines) that correctly do not change under a background
blur — an early measurement that only used the full panel understated the effect by ~5×. Measure the
variable, not the composite.

### Blur radius — 3px is past the knee

Sweeping the radius on the isolated probe shows a sharp knee and then a plateau:

| radius | 0px | 2px | **3px** | 5px | 8px | 12px |
|---|---|---|---|---|---|---|
| reduction vs bare | 0.0% | 67.5% | **68.0%** | 71.9% | 77.2% | 82.4% |

So `backdrop-blur-[3px]` captures essentially the entire benefit. Going to 8–12px buys another ~9
points of edge reduction at the cost of smearing the gradient's colour banding. **No change needed** —
the shipped value is the right one, and now that is a measured claim rather than a taste judgement.

### Fix 2 — the gutter, measured

At a 1440px dashboard content area:

| | grid width | columns | dead gutter |
|---|---|---|---|
| before | 1216px | 6 | **113px each side** |
| after | 1394px | 8 | 0 |

1216px is exactly `max-w-7xl` (1280) minus the `px-8` padding (64), centred inside the 1440px frame —
which is precisely the wide dead space either side of the thumbnails in the reported screenshot.

### Fix 1 — height chain, measured

The comms gap was reproduced faithfully using the project's **own compiled Tailwind**
(`.next/static/chunks/*.css`) with the class names copied verbatim from
`OptimizedDashboardLayout.tsx:31-98`, `JobsDashboard.tsx:1104-1106/1107/1478-1480` and
`CommsPanel.tsx:612`. Both the current and fixed versions were rendered in Chromium and the distance
from the card's bottom edge to the frame's content-box bottom was measured directly.

| viewport height | 600px | 700px | 800px | 1000px | 1200px |
|---|---|---|---|---|---|
| dead space, current code | −78px | 22px | 122px | 162px | 162px |
| dead space, fixed code | 0px | 0px | 0px | 0px | 0px |

**A prediction that the measurement falsified.** Before measuring, I reasoned that
`min-h-[520px]` would make the card's `height: 100%` resolve against the wrapper's *height property*
(480px) rather than its `min-height`-expanded used height (520px), leaving a second gap inside the
wrapper. The probe reported `gap inside wrapper: 0px` — the card filled the wrapper exactly, and the
entire defect was the wrapper being too short. The theory was wrong; without the probe it would have
gone into the code comments as fact.

**The tall-tab regression was caught the same way.** The flex chain initially looked safe to apply
unconditionally. Injecting 2400px of content showed `main.scrollHeight` collapsing from 2418px to
751px — no scrollable overflow, content unreachable — which is why the chain is now gated on
`isCommsTab`.

*Reading the harness:* `version-a.html` models the current code (and, after the fix, every non-comms
tab — their classes are unchanged); `version-b.html` models the comms tab with the flex chain applied.
The regression probe deliberately runs the tall-content test against **both**, because that is what
demonstrates why an unconditional chain is unsafe. `version-b` failing the tall probe is the *point* —
in the shipped code that combination never occurs, because the chain is gated.

### Fixes 2 and 4

Fix 1 is arithmetic on known values: frame `py-5` = 20px bottom, plus the tab's own `lg:pb-12` = 48px,
totalling 68px against 24px sides — the ~2.8× the screenshot showed. Fix 4 is the removal of a branch;
the assertion is that the widget now renders nothing until real items exist, which the harness
confirms (`null` for an empty list).

## Appendix — "Failed to save tailoring mode" (regression from the earlier score-integrity work)

Reported as a runtime console error at `JobsDashboard.tsx:1021`.

**Root cause: a wrong HTTP verb, introduced when the endpoint was repointed.**

The earlier work moved the canonical tailoring-mode store to `User.settings.cvTailoringMode` (what
document generation reads) and repointed the jobs-hub toggle from `/api/job-search-profile` to
`/api/user/settings`. The `method: 'PATCH'` was carried over — but `/api/user/settings` exports
**`GET` and `PUT` only**, so every save returned **405** and the toggle silently reverted.

```tsx
// before — 405, silently reverted
const res = await fetch('/api/user/settings', { method: 'PATCH', … });

// after
const res = await fetch('/api/user/settings', { method: 'PUT', … });
```

Every other caller of that route (`dashboard/settings`, `Step3CV`) already used PUT; the jobs-hub
toggle was the only outlier.

**Why nothing caught it.** `tsc`, ESLint, the test suite and `npm run build` were all green, and they
were green *before* this fix too — a wrong HTTP method is not expressible in the type system and only
surfaces at runtime. This is the same blind spot as the CSS constant in fix 1: **the checks that
passed could not have failed.** Worth remembering when a change swaps an endpoint, a verb, an env var
name, or any other string-keyed contract.

**Secondary fix — visible failure.** The handler reverted the optimistic update and logged to the
console only, which is indistinguishable from "the toggle just doesn't stick" (which is how it was
reported). It now also raises a destructive toast, so a failed save is visible instead of silent.

**Verified persistence path:** `parseCvTailoringMode('normal')` → `'standard'`, matching the
`User.settings.cvTailoringMode` enum `['standard','standout']` (declared in `models/User.ts:808`, so
Mongoose strict mode will not strip it). The route also mirrors the value to
`JobSearchProfile.cvTailoringMode` best-effort, and `PATCH /api/jobs/preferences` mirrors in the
reverse direction — both directions covered, no competing-writer divergence.
